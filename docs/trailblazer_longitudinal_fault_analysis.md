# 2021~22 Chevrolet Trailblazer 롱컨 오류 분석 및 수정 기록

## 빠르게 읽는 순서

- 처음 보는 사람: **2 → 3 → 5 → 6 → 11 → 14장**
- CAN 원인을 자세히 볼 사람: **4 → 7장**
- 실제 수정 코드를 확인할 사람: **9 → 10장**
- 다음 실차 시험을 진행할 사람: **12장**

2장은 쉬운 비유, 3장은 각 파일이 어떤 주행인지, 5장은 운전자가 본 경고와 로그의 대응, 6장은 초 단위 타임라인이다. 이미 배경을 아는 경우 11장의 해결/미해결 표부터 읽어도 된다.

## 1. 문서 목적과 현재 결론

이 문서는 2021~22 Chevrolet Trailblazer에서 openpilot 종방향 제어(이하 롱컨)를 사용할 때 발생한 크루즈 오류, ACC 해제, 간헐적 긴급제동/전방카메라 경고, CAN 오류를 원본 rlog로 분석한 결과와 `trailblazer_long_fix` 브랜치의 수정 내역을 한곳에 정리한다.

현재까지 로그로 확인된 직접적인 프로토콜 문제는 모두 코드로 수정됐다. 2026-08-07에 추가된 냉간 시동·주행 로그에서는 기존 수정 뒤에도 남은 두 조건을 새로 확인했다.

1. `0x2CB` 가스·리젠 명령 체크섬의 24비트 자리올림 오류
2. 순정 종방향 명령과 openpilot `0x2CB`/`0x315` 사이의 롤링 카운터 불일치
3. 이 연식 Trailblazer의 순정 `0x370` ACC 상태 비트를 일반 GM 값으로 덮어쓰던 문제
4. 약 0.5 km/h처럼 거의 정차한 상태에서 처음 인게이지할 때 ECM이 오류를 내는 문제
5. 운전자 가속페달 입력과 `longActive` 해제 사이의 한 제어 주기 경합으로 `0x2CB`/`0x315`가 Panda에서 차단되는 문제
6. 냉간 시동 때 실제 순정 `0x2CB`가 `0x2CD`보다 한 주기 늦는데도 `0x2CD` 위상으로 먼저 명령하던 문제
7. 순정 카메라가 종방향 권한을 먼저 해제한 뒤에도 openpilot이 약 170 ms 동안 활성 제동 명령을 계속 보내던 문제

최종 코드 커밋은 [`fa2b434`](https://github.com/leehyuk1108/carrotpilot/commit/fa2b434050c38b1344de5ce0f275c8b89d76f2a7)이다. 2026-08-07 로그는 그 이전 커밋 `46bddc25`로 주행했으므로, 새 카운터·순정 권한 보호의 실차 검증은 아직 남아 있다. 따라서 상태는 **로그 원인 확인 및 코드 수정 완료, 최종 실차 검증 대기**로 보는 것이 정확하다.

## 2. 먼저 아주 쉽게 설명하면

### 2.1 차량은 40 ms마다 네 가지가 맞는지 확인한다

롱컨을 사용하는 동안 openpilot은 약 40 ms마다 가속과 제동에 관한 CAN 메시지를 보낸다. 이 Trailblazer는 메시지에 들어 있는 가속·제동 숫자만 보는 것이 아니라 다음 항목을 한 묶음으로 확인하는 것으로 보인다.

1. 이번 메시지가 몇 번째인지 나타내는 **카운터**
2. 내용이 전송 중 변하지 않았는지 확인하는 **체크섬**
3. 현재 ACC가 어떤 상태인지 나타내는 **상태 비트**
4. 정해진 주기마다 메시지가 빠지지 않고 들어오는지 나타내는 **연속성**

이를 등기우편에 비유할 수 있다.

| CAN 항목 | 쉬운 비유 | 잘못됐을 때 차량이 보는 상황 |
|---|---|---|
| 롤링 카운터 | 봉투의 연속 번호 `0→1→2→3→0` | 1번 다음에 갑자기 3번 봉투가 도착함 |
| 체크섬 | 봉투의 위조 방지 도장 | 내용은 그럴듯하지만 도장이 맞지 않음 |
| `0x370` 상태 | 봉투 표지의 부서·업무 상태 | Trailblazer용 봉투에 다른 GM 차종의 상태가 적힘 |
| 40 ms 주기 | 매번 도착해야 하는 정기 보고 | 보안 게이트가 한 봉투를 막아 보고가 한 번 빠짐 |
| Panda safety | 위험 명령을 막는 보안 게이트 | 가속페달 중 제동 명령처럼 위험할 수 있는 봉투를 차단함 |

순정 ACC는 위 네 가지를 차량이 기대하는 방식으로 보낸다. 초기 openpilot 롱컨은 가속·제동 값 자체는 대체로 맞았지만, 특정 순간에 번호·도장·표지·연속성 중 하나가 어긋났다. 차량은 이를 즉시 또는 누적해서 감지하고 크루즈를 해제했다.

### 2.2 처음에는 왜 정말 랜덤처럼 보였는가

가장 처음 확인된 체크섬 버그는 모든 프레임에서 발생하지 않았다. 명령값의 하위 바이트가 경계를 넘을 때만 자리올림이 틀렸다.

실제 오류 프레임 하나를 간단히 보면 다음과 같다.

```text
계산 대상 24비트 값: 0x42CE00
카운터:              0

순정 방식: 0x1000000 - 0x42CE00 - 0 = 0xBD3200
기존 코드 결과:                         0xBD3100
차이:                                  0x000100
```

평소 명령값에서는 두 계산 결과가 우연히 같다가 특정 값에서만 `0x100` 차이가 났다. 따라서 같은 길을 달리고 있어도 차량이 요구한 가속·리젠 값이 그 경계를 통과하는 순간에만 오류가 발생했다.

쉽게 말해, **매번 틀리는 시계가 아니라 특정 숫자가 표시될 때만 한 칸 틀리는 시계**였기 때문에 운전자에게는 랜덤처럼 보였다.

### 2.3 수정 전과 최종 수정 후의 차이

정상적인 최종 흐름은 다음과 같다.

```text
실제 순정 카메라 0x2CB 도착, counter=3
              ↓ 같은 제어 주기
openpilot 0x2CB 전송, counter=3, 올바른 checksum
openpilot 0x315 전송, counter=3, 올바른 checksum
openpilot 0x370 전송, Trailblazer 순정 상태 비트 유지
              ↓
Panda safety 허용 → 차량 수신
```

운전자가 가속페달을 밟는 순간에는 다음처럼 바뀐다.

```text
가속페달 입력 감지
       ↓ 같은 명령 주기
0x2CB = -500 (inactive/중립)
0x315 = 0    (openpilot 제동 없음)
카운터와 ACC 상태는 끊지 않고 유지
       ↓
Panda safety 허용 → 메시지 누락 없음
```

즉 가속페달을 밟았다고 ACC 통신 자체를 끊는 것이 아니라, **“ACC 상태는 계속 살아 있지만 지금은 운전자가 직접 가속하므로 openpilot 가속·제동은 중립”**이라고 안전하게 전달한다.

순정 카메라가 ACC 권한을 먼저 끄는 경우에는 의미가 다르다. 이때는 순정 `0x2CB`의 `GasRegenCmdActive=0`을 받은 바로 그 주기에 openpilot도 활성 비트를 끄고 명령을 중립화한다.

```text
순정 0x2CB: GasRegenCmdActive 1 → 0
                    ↓ 같은 주기
openpilot 0x2CB = -500, active=0
openpilot 0x315 = 0
openpilot 인게이지 해제 요청
```

쉽게 말해 차량이 “이제 ACC 제동 명령을 받지 않겠다”고 통보했는데 openpilot이 뒤늦게 활성 봉투를 더 보내는 상황을 없앴다.

### 2.4 현재 상태를 한 문장으로 정리하면

체크섬, 카운터, Trailblazer 고유 상태 비트, 저속 인게이지, 가속페달 전환 누락, 냉간 카운터 위상, 순정 권한 해제 지연까지 로그에서 찾은 문제는 모두 수정했다. 다만 마지막 두 수정이 적용된 `fa2b434`로 만든 실차 rlog가 아직 없으므로 냉간 시동과 실제 주행으로 확인해야 한다.

## 3. 차량 및 로그 구분

대상은 `CHEVROLET_TRAILBLAZER`로 식별되는 2021~22 Trailblazer ACC 차량이다. 신형 Trailblazer 및 다른 GM 차량에서는 같은 증상이 보고되지 않았으며, 모든 변경은 해당 Trailblazer 핑거프린트와 카메라 롱컨 경로에 한정했다.

### 3.1 처음 제공된 네 가지 기준 로그

처음 제공된 네 가지 파일명은 수집자가 분류를 위해 붙인 이름이다. 이름에 들어 있는 `0`과 `1`은 파일 순번이 아니라 openpilot 인게이지 여부를 뜻한다.

| 로그 | 차량 롱컨 설정 | openpilot 상태 | 실제 종방향 제어 주체 |
|---|---|---|---|
| `롱컨 0` | 켬 | 디스인게이지 | 순정 상태 관찰, openpilot 롱컨 비활성 |
| `롱컨 1` | 켬 | 인게이지 | openpilot 롱컨 |
| `비롱컨 0` | 끔 | 디스인게이지 | 순정 ACC 비활성 |
| `비롱컨 1` | 끔 | 인게이지 | 차량 순정 ACC |

### 3.2 문서에서 사용하는 로그 번호

원래 폴더명만으로는 제3자가 주행 조건을 알 수 없으므로 이 문서에서는 `L01`부터 `L23`까지 별도 번호와 설명 이름을 사용한다. 아래 표의 “실제 파일”은 수집된 원래 폴더/segment 이름이며 변경하지 않았다.

openpilot의 `rlog.zst`는 보통 약 1분 단위 segment다. 예를 들어 다음 경로에서 마지막 `62`는 같은 route의 62번 segment라는 뜻이다.

```text
또에러/0000013a--9977e36ddd--62/rlog.zst
                                  └─ 약 1분짜리 segment 번호
```

따라서 한 파일의 길이가 약 60초여도 실제 주행 전체가 1분이라는 뜻은 아니다. `L16`은 한 시간가량 이어진 route 중 62번 segment이고, `L14`처럼 파일 시작 전부터 오류가 난 경우에는 바로 전 segment가 있어야 최초 원인을 볼 수 있다. 반대로 `롱컨 0/rlog.zst`처럼 route 폴더 없이 바로 있는 파일은 수집 과정에서 해당 segment만 따로 풀어 놓은 것이다.

### 3.3 파일을 서로 어떻게 비교했는가

- `L01`·`L02`: 같은 차량에서 순정 통신이 정상이라는 기준
- `L03`·`L04`: 롱컨 설정만 켠 경우와 실제 인게이지한 경우의 차이
- `L05`·`L06`: 수정 전 랜덤 크루즈 오류의 반복성 확인
- `L07`·`L08`: 체크섬과 카운터를 수정한 뒤 남은 저속/상태 문제 분리
- `L09`~`L12`: 후진 자체가 CAN 붕괴를 만드는지 순정/롱컨 교차 검증
- `L13`·`L14`: CAN 붕괴가 시작되는 구간과 이미 붕괴한 후속 구간 구분
- `L15`·`L16`: `0x370`까지 수정한 최신 상태에서 정상 사례와 실패 사례 비교
- `L17`~`L19`: 서로 다른 두 냉간 시동에서 같은 EBCM unavailable과 카운터 위상 재현
- `L20`·`L21`: 사용자가 지목한 segment 경계를 이어 실제 크루즈 오류 시작점을 확인
- `L22`·`L23`: 조향 알림을 종방향 크루즈/CAN 오류와 분리

특히 `L15`와 `L16`은 같은 커밋을 사용했다. 둘 다 가속페달 순간 Panda 차단이 있었지만 `L15`는 계속 정상이고 `L16`은 약 5.36초 뒤 CAN이 붕괴했다. 따라서 한 번의 프레임 누락이 항상 즉시 고장을 만들지는 않지만, 다른 프로토콜 문제가 제거된 최신 상태에서 마지막으로 남은 공통 위험 요소가 가속 오버라이드 전환임을 확인할 수 있었다.

`L14`는 첫 `carState`부터 `canValid=false`, `canTimeout=true`, `accFaulted=true`였다. 따라서 이 파일만으로 최초 원인을 찾을 수 없고, 앞 구간에서 이미 발생한 CAN 붕괴가 같은 형태로 계속된다는 사실만 확인할 수 있다.

## 4. 분석 방법과 주요 CAN 메시지

각 rlog에서 다음 항목을 같은 기준으로 비교했다.

- `initData`: 실제 사용 커밋, 브랜치, dirty 상태
- `carParams`: 롱컨 사용 여부와 차량 핑거프린트
- `carState`: `accFaulted`, `canValid`, `canTimeout`, 속도, 기어, 가속·브레이크 입력
- `carControl`: `enabled`, `longActive`, 요청 가속도
- `onroadEvents`: `accFaulted`, `canBusMissing`, `radarFault`, `steerTempUnavailable` 등
- Panda 상태: `safetyTxBlocked`, CAN ACK 오류, error-passive, 전송 버퍼 오버플로, CAN 코어 리셋
- 물리 CAN과 loopback: 순정 카메라 프레임, 정상 송신 프레임, 안전 차단 프레임
- `0x2CB`/`0x315` 체크섬과 카운터, `0x370`의 순정 보호 상태 비트
- 순정 `0x2CD` 수신부터 openpilot 명령 송신까지의 시간

주요 메시지는 다음과 같다.

| 주소 | 이름/역할 | 분석에서의 의미 |
|---:|---|---|
| `0x1C4` | `AcceleratorPedal2` | 운전자 가속페달 및 순정 크루즈 상태 |
| `0x2CB` | `ASCMGasRegenCmd` | 가스·리젠 명령, 활성 비트, 카운터, 24비트 체크섬 |
| `0x315` | `EBCMFrictionBrakeCmd` | 마찰제동 명령, 모드, 카운터, 체크섬 |
| `0x2CD` | `ASCM_2CD` | 순정 카메라에서 유지되는 롤링 카운터 기준 |
| `0x370` | `ASCMActiveCruiseControlStatus` | ACC 상태, 계기판 표시, 상태/상수 비트 |

로그의 CAN source는 다음처럼 해석했다.

| source | 의미 |
|---:|---|
| `2` | 카메라측에서 관찰된 순정 프레임 |
| `128` | Panda가 허용해 실제 송신한 loopback 프레임 |
| `192` 이상 | Panda safety가 차단한 송신 프레임 |

## 5. 운전자가 본 현상과 로그의 의미

같은 “오류”라는 표현도 로그에서는 서로 다른 상태다. 운전자 화면과 실제 로그를 다음처럼 구분해야 한다.

| 운전자가 본 현상 | 로그에서 확인할 항목 | 이 분석에서의 해석 |
|---|---|---|
| 경고음과 함께 ACC/openpilot 해제 | `accFaulted=true`, `canValid=true` | 차량 ACC ECU가 명령 내용을 거부한 **크루즈 단독 오류**. CAN 선 자체는 살아 있음 |
| 바로 다시 인게이지 가능 | 잠시 후 `accFaulted=false`, 카메라 source 2 지속 | ECU의 일시적인 명령 검증 오류가 해제됨 |
| CAN 오류/전방카메라 사용 불가 | source 2 중단, `canTimeout`, `canValid=false`, `canBusMissing` | 카메라측 통신이 실제로 사라진 **CAN 붕괴** |
| 레이더 오류까지 연속 표시 | `radarFault`, `locationdTemporaryError`가 뒤따름 | 최초 원인이라기보다 필수 CAN 입력이 사라진 뒤 발생한 2차 오류 |
| 긴급제동 오류 표시 | ACC fault 및 `0x315`/`0x2CB` 명령 이상과 함께 관찰 | AEB/ACC가 공유하는 전방카메라·제동 상태 이상 경고로 추정. rlog에 정비 DTC가 없어 정확한 계기판 문구 원인은 확정 불가 |
| 후진할 때 경고가 더 뚜렷해짐 | 오류 이후 R 진입, 이미 `canValid=false` | 후진이 최초 원인이 아니라 이미 끊긴 카메라 상태를 차량이 다시 점검하면서 경고가 표시된 것 |
| 잠시 뒤 혼자 정상 복귀 | source 2 수신 재개 또는 다음 주행/segment에서 정상 | 카메라/게이트웨이 통신 경로가 재초기화된 것으로 해석 |
| `steerTempUnavailable` | CAN은 valid이고 ACC fault 없음 | 조향의 일시적 사용 불가 이벤트. 이번 종방향 CAN 오류와 별개 |
| 시동 직후 파워스티어링·ESC 경고 | CAN/Panda는 정상, EBCM `FrictionBrakeUnavailable=1` | 냉간 순정 `0x2CB`보다 한 카운터 빠른 openpilot 명령과 연결 |
| 약하게 브레이크를 밟을 때 크루즈 오류 | 순정 `GasRegenCmdActive=0` 뒤 openpilot active 제동 지속 | 순정 ACC가 권한을 먼저 철회했는데 openpilot 해제가 늦은 상태 충돌 |

가장 중요한 구분은 다음 두 줄이다.

```text
accFaulted=true + canValid=true  → 크루즈 메시지 검증 오류
accFaulted=true + canValid=false → 카메라 CAN까지 실제로 끊어진 상태
```

### 6.3 `L06` 단발 크루즈 오류 교차 검증

실제 파일은 `오류 2/rlog.zst`다.

| 55.3354초 | `canValid=false` |
| 55.3648초 | CAN 붕괴에 따른 `accFaulted=true` |
| 로그 종료 | Panda bus 0 `ackError`, error-passive, CAN core reset 61회 |

앞의 크루즈 오류는 잘못된 체크섬과 직접 연결된다. 약 12.6초 뒤 발생한 CAN 붕괴는 체크섬·카운터·상태 불일치가 누적된 수정 전 환경에서 발생했으며, 후진이나 정차가 원인이 아니다.

### 6.5 `L07` 체크섬·카운터 수정 후 저속 인게이지

실제 파일은 `new1/...--11/rlog.zst`다. 이 버전에서는 체크섬 오류가 0회이고 순정 `0x2CD` 카운터도 일치했다. 하지만 `0x370`은 여전히 일반 GM 상태를 사용했다.

| 50.8696초 | 운전자 가속페달 입력 |

이 로그 하나에는 저속 경계와 잘못된 `0x370` 상태라는 두 조건이 겹친다. 어느 하나만으로 100% 단정하지 않고, 5 km/h 가드와 순정 `0x370` 보존을 각각 적용해 두 가능성을 모두 제거했다.

### 6.6 `L13` 가속 전환 뒤 CAN 붕괴 및 후진

실제 파일은 `15분주행 후신시 CAN ER/...--8/rlog.zst`다. 폴더명은 수집자가 “약 15분 주행 뒤 후진 시 경고를 봄”이라는 뜻으로 붙였지만, 로그 순서는 후진 전에 CAN이 이미 끊겼음을 보여준다.

## 7. 확정된 원인과 증거

### 7.1 원래의 랜덤 크루즈 오류: `0x2CB` 체크섬 자리올림 오류

수정 전 구현은 24비트 체크섬을 바이트별 보수로 계산했다. 순정 ASCM은 세 바이트를 하나의 24비트 정수로 빼므로 하위 바이트에서 발생하는 carry/borrow가 상위 바이트까지 전달돼야 한다. 기존 방식은 특정 명령값과 카운터 조합에서 이 전달을 잃어 체크섬이 `0x100`만큼 틀렸다.

오류는 항상 발생하지 않고 가스·리젠 명령값의 바이트 경계에서만 발생했다. 이 때문에 주행 중에는 규칙 없는 랜덤 크루즈 오류처럼 보였다.

로그에서는 잘못된 `0x2CB` 뒤 약 52~61 ms 후 `accFaulted`가 발생했다.

| 로그 | 잘못된 `0x2CB` 시각 | `accFaulted` 시각 | 차이 |
|---|---:|---:|---:|
| `L05` 반복 크루즈 오류 | 2.7886초 | 2.8500초 | 61.4 ms |
| `L05` 반복 크루즈 오류 | 9.0282초 | 9.0801초 | 51.9 ms |
| `L05` 반복 크루즈 오류 | 29.3488초 | 29.4004초 | 51.6 ms |
| `L06` 단발 크루즈 오류 | 8.0779초 | 8.1301초 | 52.2 ms |
| `L04` 최초 롱컨 복합 오류 | 42.2732초 | 42.3253초 | 52.1 ms |

이 반복 정렬은 원래 크루즈 오류의 가장 강한 직접 증거다. `f5bebb6` 이후 로그에서는 `0x2CB` 체크섬 오류가 0회다.

### 7.2 순정 기준과 다른 롤링 카운터: `0x2CD` 추종에서 실제 `0x2CB` 추종으로

수정 전 openpilot은 자체 25 Hz 제어 프레임 번호로 `0x2CB`와 `0x315` 카운터를 만들었다. 해당 Trailblazer 세대는 카메라에서 계속 들어오는 `0x2CD` 카운터와 교체 송신되는 종방향 명령을 교차 확인하는 것으로 나타났다.

`L05`와 `L06`에서는 가까운 `0x2CD`에 대해 openpilot 카운터가 지속적으로 어긋났다. 첫 수정은 새 `0x2CD`가 수신된 주기에만 명령 그룹을 만들고 그 카운터를 사용했다. ACC가 이미 활성인 주행에서는 이것이 맞았고, 최신 `d8ebe59` 두 로그에서도 다음처럼 일치했다.

최신 `d8ebe59` 두 로그의 합계는 다음과 같다.

- `0x2CD`: 총 2,360주기
- `0x2CB`: Panda 차단 프레임을 포함해 2,360/2,360 카운터 일치
- `0x315`: Panda 차단 프레임을 포함해 2,360/2,360 카운터 일치
- `0x2CB` 체크섬 오류: 0회
- `0x315` 체크섬 오류: 0회
- `0x2CD`에서 openpilot 명령까지: 중앙값 약 9.7 ms

따라서 당시 주행 중 CAN 붕괴는 카운터 누락이나 체크섬 재발로 설명할 수 없었다. 그러나 `L18`과 `L19` 냉간 시동에서는 더 정확한 규칙이 드러났다. 실제 순정 종방향 명령 `0x2CB`는 냉간·비활성 상태에서 `0x2CD`보다 약 40 ms 늦고 한 카운터 뒤에 있다가, ACC 활성 뒤에는 `0x2CD`와 정렬됐다.

즉 `0x2CD`는 평소에는 좋은 간접 기준이지만 항상 실제 명령의 카운터는 아니었다. 최종 수정은 간접 기준을 추정하지 않고 카메라에서 들어오는 실제 순정 `ASCMGasRegenCmd(0x2CB)`의 도착 주기와 카운터를 그대로 사용한다. 따라서 냉간 지연 위상과 주행 중 정렬 위상을 별도 조건문 없이 모두 따른다.

### 7.3 Trailblazer 고유 `0x370` ACC 상태

일반 GM 경로는 openpilot ACC 상태를 만들 때 다음 값을 사용했다.

```text
ACCCruiseState = 0
ACCAlwaysOne   = 1
ACCAlwaysOne2  = 1
```

해당 Trailblazer의 순정 카메라 값은 다음과 같았다.

```text
ACCCruiseState = 2
ACCAlwaysOne   = 0
ACCAlwaysOne2  = 0
```

`L07`은 카운터 동기화와 체크섬 수정이 이미 적용돼 있었고 두 항목 모두 정상이었지만, openpilot이 생성한 `0x370` 1,498개가 계속 순정 상태와 달랐다. 이 로그에서 51.321초에 CAN 단절 없는 짧은 `accFaulted`가 발생했다. 같은 코드의 다음 구간인 `L08`에서는 같은 불일치가 있었지만 1분 동안 오류가 나지 않아, 차량 ECU의 판정이 누적 상태나 다른 조건에 따라 간헐적으로 나타남을 보여준다.

수정 후에는 순정 카메라 `0x370` 전체를 템플릿으로 보관한다.

- 롱컨 비활성, P/R/N: 순정 payload를 그대로 전달
- 롱컨 활성, D: 순정 프로토콜 상태를 유지하고 표시용 필드만 변경
- 순정 템플릿을 아직 받지 못한 시작 구간: 임의의 일반 GM 상태를 보내지 않고 첫 순정 프레임을 기다림

`d8ebe59` 로그에서는 지속적인 상태 불일치가 사라졌다. `L16`에서 `ACCResumeButton` 전환이 순정 대비 한 주기 늦게 반영된 경우가 2회 있었지만, 12.538초와 17.538초로 실제 오류 시각과 17초 이상 떨어져 있었고 그때 크루즈/CAN 오류는 없었다.

### 7.4 거의 정차한 상태의 최초 인게이지

약 0.5 km/h 상태에서 롱컨 인게이지를 시도한 로그에서 한 번 크루즈 오류가 발생했다. 완전 정지 상태와 달리 차량은 미세하게 움직이고 있었지만, ECM이 요구하는 제동 상태가 충분하지 않은 경계 조건이었다.

Trailblazer 롱컨의 `minEnableSpeed`를 5 km/h로 설정했다.

- 0보다 크고 5 km/h 미만: 인게이지 차단 및 `belowEngageSpeed`
- 완전 정지 + 브레이크: 기존 openpilot 정차 인게이지 예외를 유지
- 비롱컨 및 다른 GM 차량: 변경 없음

### 7.5 가속페달 입력 순간의 Panda 차단

운전자가 가속페달을 밟으면 Panda는 원본 `0x1C4`를 받는 즉시 `gas_pressed`를 갱신한다. 반면 openpilot의 `carControl.longActive` 해제는 다음 제어 갱신에 반영될 수 있다. 그 사이 한 주기 동안 이전의 가스·리젠 또는 제동 명령이 만들어지면 Panda safety가 해당 프레임을 차단한다.

#### `L16` 가속 경합 오류 타임라인

| 시각 | 상태 |
|---:|---|
| 29.1399초 | `carState.gasPressed=true`, 약 9.54 km/h |
| 29.144초 | `carControl.longActive=false` 반영 |
| 29.1488초 | `0x2CB`와 `0x315`가 Panda에서 동시 차단 |
| 34.5088초 | 카메라 source 2의 마지막 프레임 |
| 34.5489초 | Panda bus 0 ACK 오류/error-passive 시작 |
| 34.8301초 | `accFaulted=true` |
| 34.9211초 | `canTimeout=true` |
| 34.9300초 | `canValid=false` |

차단된 명령은 다음과 같다.

```text
0x2CB c142af5000bd50ad
  RollingCounter=3, GasRegenCmdActive=1, GasRegenCmd=-540

0x315 af71508c03
  RollingCounter=3, FrictionBrakeMode=10, FrictionBrakeCmd=-143
```

Panda safety는 가속페달 입력 중 가스·리젠 명령으로 정확한 inactive 값 `-500`만 허용하고, 마찰제동은 `0`만 허용한다. 따라서 카운터와 체크섬이 맞더라도 위 두 프레임은 안전 규칙에 따라 차단됐다. 다음 주기는 비활성 명령으로 정상 송신됐지만 이미 한 개 카운터 그룹이 빠진 상태였다.

#### 다른 로그와의 교차 검증

| 로그 | 가속 입력 후 차단 | 카메라 CAN 중단 | 결과 |
|---|---|---|---|
| `L13` 장시간 주행 뒤 CAN 붕괴 | 25.938초, `0x2CB` | 36.259초 | 36.560초 `accFaulted`, 36.691초 CAN invalid |
| `L15` 최신 정상 지속 구간 | 37.658초, `0x2CB` | 없음 | 이후 약 22초 동안 정상 |
| `L16` 최종 수정 직전 경합 오류 | 29.149초, `0x2CB`+`0x315` | 34.509초 | 34.830초 `accFaulted`, 34.930초 CAN invalid |

한 번의 차단이 항상 즉시 CAN 붕괴를 만들지는 않는다. 그러나 수정된 프로토콜에서 실제 붕괴가 발생한 두 로그 모두 그 전에 가속 오버라이드 차단이 있었고, 최신 로그에는 그 외 체크섬·카운터·상태 오류가 없었다. 이 때문에 남아 있던 마지막 직접 트리거로 판단했다.

최종 수정은 Trailblazer에서 `CS.out.gasPressed`가 참인 같은 명령 주기에 다음 값을 강제한다.

```text
0x2CB GasRegenCmd       = -500 (inactive)
0x315 FrictionBrakeCmd = 0
at_full_stop           = false
near_stop              = false
```

`GasRegenCmdActive`와 순정 롤링 카운터는 연속성을 위해 유지한다. 이는 순정 ACC도 운전자 가속 오버라이드 동안 ACC 상태 자체는 유지하는 것과 같은 방향이며, Panda 안전 제한을 완화하지 않는다.

### 7.6 크루즈 오류와 CAN 오류의 관계

로그에는 두 종류의 현상이 구분된다.

1. **크루즈 단독 오류**: `accFaulted=true`지만 `canValid=true`이고 카메라 source 2가 계속 수신됨
2. **카메라 CAN 붕괴**: source 2 중단 후 ACK 오류, error-passive, `canTimeout`, `canValid=false`, `canBusMissing` 순으로 진행

수정 전 복합 오류 로그인 `L04`에도 실제 CAN 붕괴가 있었다.

- 42.325초: 잘못된 체크섬 뒤 크루즈 오류
- 43.355초: 크루즈 오류 해제
- 46.056초: 다시 크루즈 활성
- 54.914초: 카메라 source 2 중단
- 55.305초: `canTimeout`
- 55.335초: `canValid=false`
- 당시 약 45.9 km/h, D 기어
- Panda bus 0: `ackError`, error-passive, CAN core reset 61회

따라서 CAN 오류는 패치가 새로 만든 현상으로만 볼 수 없다. 가장 일관된 해석은 잘못되거나 누락된 종방향 메시지 그룹이 먼저 ACC 감시 로직을 자극하고, 조건이 심해지면 카메라/차량측 통신 경로가 재시작되면서 Panda 송신이 ACK를 받지 못한다는 것이다. 다만 ECU 내부 펌웨어와 정비 DTC를 확보하지 않았으므로, ECU 내부의 정확한 리셋 조건은 로그만으로 확정할 수 없다.

### 7.7 냉간 시동의 파워스티어링·ESC 경고: 실제 `0x2CB`보다 한 주기 빠른 명령

`L18`과 `L19`에서는 경고 시각에 Panda fault, 체크섬 오류, 차단 프레임, `canValid=false`가 없었다. 두 로그에서 공통으로 바뀐 차량 상태는 EBCM의 `FrictionBrakeUnavailable 0→1`이었다.

- `L18`: 1.2498초, D, 약 6.02 km/h, 가속페달 입력 상태
- `L19`: 16.6546초, R, 거의 0 km/h, 브레이크를 놓은 직후

기어와 속도가 다른데도 같은 현상이 반복됐으므로 D 출발이나 후진 자체가 공통 원인은 아니다. 공통점은 냉간·비활성 카운터 위상이다. `L19`의 오류 직전 프레임은 다음과 같다.

| 시각 | CAN 동작 |
|---:|---|
| 16.592초 | 순정 `0x2CD counter=0` |
| 16.632초 | 실제 순정 `0x2CB/0x315 counter=0`; 동시에 다음 `0x2CD counter=1` |
| 16.642초 | 기존 openpilot이 `0x2CD`를 따라 `0x2CB/0x315 counter=1`을 먼저 송신 |
| 16.6546초 | EBCM `FrictionBrakeUnavailable=1` |

쉽게 말하면 순정 제동기가 아직 0번 주문서를 처리하는데 openpilot이 보조 시계만 보고 1번 주문서를 먼저 제출했다. ACC가 활성인 평상시에는 두 시계가 맞아 문제가 숨었지만 냉간 시동에서는 약 40 ms 차이가 났다.

`fa2b434`는 다음처럼 수정한다.

1. `0x2CD`가 아니라 실제 카메라 `0x2CB`가 새로 들어온 주기에만 종방향 명령 그룹을 만든다.
2. 실제 `0x2CB`의 카운터를 `0x2CB`와 `0x315`에 그대로 사용한다.
3. 부팅 중 `0x2CB`와 `0x370` 기준을 아직 못 받았으면 임의의 첫 명령을 보내지 않는다.
4. 이 두 메시지는 동기화 참고값으로만 파싱해, 늦게 도착했다는 이유만으로 카메라 CAN 전체를 invalid 처리하지 않는다.

4번은 부팅 직후 openpilot CAN 경고 가능성을 함께 줄이지만, 계기판 파워스티어링·ESC 경고의 직접 로그 근거는 1~2번의 카운터 선행과 EBCM unavailable이다.

### 7.8 약한 제동의 크루즈 오류: 순정 권한 해제를 170 ms 늦게 따름

`L20`의 38초 부근에는 체크섬 오류, 카운터 손상, Panda 차단, 물리 CAN 오류가 없었다. 대신 순정 카메라와 openpilot의 활성 상태가 잠시 서로 달랐다.

| 시각 | 상태 |
|---:|---|
| 37.9688초 | 순정 `0x2CB GasRegenCmdActive=0`; 순정 가스·리젠/제동 명령 비활성 |
| 38.0084초 | 순정 `0x370 ACCCmdActive=0` |
| 38.1384초 | 기존 openpilot은 여전히 active 상태로 제동 명령 `52` 송신 |
| 38.149초 | 차량 `CruiseState 1→3(FAULTED)` |
| 38.1507초 | openpilot `accFaulted=true` |
| 38.1789초 | openpilot 종방향 명령이 뒤늦게 inactive로 전환 |

순정 카메라는 먼저 “ACC 제어 권한 없음”을 선언했지만 기존 코드는 `CC.enabled`가 내려갈 때까지 활성 명령을 계속 만들었다. 마지막 active 제동과 차량 fault는 약 11 ms 차이이며, 순정 `0x2CB` 비활성부터는 약 170 ms 동안 겹치지 않는 상태가 지속됐다.

`fa2b434`는 실제 순정 `0x2CB`의 활성 비트를 매 주기 읽는다. `true→false`가 되는 같은 주기에 가스·리젠 `-500`, 제동 `0`, 정차/근접정차 비트 false, `GasRegenCmdActive=false`를 강제한다. 또한 순정 `0x370 ACCCmdActive`가 false면 그 inactive 상태를 그대로 유지하고, cancel 버튼 이벤트를 만들어 openpilot도 즉시 디스인게이지하도록 한다.

이 보호는 Trailblazer 핑거프린트에만 적용된다. 다른 GM 차종은 기존 frame 기반 25 Hz 일정과 `CC.enabled` 동작을 그대로 사용한다.

## 8. 후진 및 하드웨어 원인 검토

### 8.1 후진은 최초 원인이 아님

비롱컨 후진 로그 2개와 롱컨 후진 로그 2개에서 후진 자체로 `accFaulted`, `canTimeout`, `canValid=false`, Panda ACK 오류가 발생하지 않았다.

`L13` 장시간 주행 뒤 CAN 붕괴 로그에서는 순서가 다음과 같다.

1. 25.938초: 가속 오버라이드 `0x2CB` 차단
2. 36.259초: 카메라 CAN 중단
3. 36.560초: `accFaulted`
4. 36.691초: `canValid=false`
5. 37.090초: 그 후에 R 진입

즉 후진 때문에 CAN이 끊긴 것이 아니라, 이미 끊긴 상태에서 후진하여 계기판의 전방카메라 사용 불가 경고가 더 눈에 띄게 나타난 것이다. 다시 D로 전환하고 차량 네트워크가 회복되면서 정상으로 돌아온 현상과도 일치한다.

그래도 P/R/N에서 openpilot이 일반 GM `0x370`을 보내지 않도록, 현재 코드는 순정 inactive 상태를 그대로 유지한다.

### 8.2 하드웨어 불량 가능성이 낮은 이유

다음 이유로 전방카메라 전원, 커넥터, 하네스, Panda 트랜시버의 개별 불량은 주원인에서 제외했다.

- 같은 연식 차량에서 반복적으로 같은 증상이 보고됨
- 같은 차량과 하드웨어에서 순정 ACC는 정상
- 비롱컨 로그에서는 후진과 주행 모두 source 2가 유지되고 Panda 오류 증가가 없음
- 크루즈 오류 시각이 잘못된 체크섬 뒤 52 ms 전후로 반복 정렬됨
- 수정 단계에 따라 체크섬, 카운터, 상태 비트, 가속 오버라이드 차단이 로그에서 순차적으로 사라짐

CAN ACK 오류는 실제로 존재하지만, 위 증거를 종합하면 하드웨어 접촉불량이 최초 원인이라기보다 차량이 비정상 ACC 메시지 흐름에 반응한 뒤 나타나는 2차 현상으로 보는 편이 타당하다.

`ACCResumeButton` 지연은 현재 로그에서 오류를 만들었다는 증거가 없다. 반면 냉간 전송 위상은 `L18`·`L19`에서 EBCM unavailable 직전 같은 형태로 재현됐으므로 실제 `0x2CB` 직접 추종으로 수정했다.

## 13. 부가 관찰

`L15` 최신 정상 지속 로그에는 사용자가 체감한 일시적인 CAN 경고와 달리 다음 항목이 없었다.

- `canValid=false`
- `canTimeout=true`
- `canBusMissing`
- Panda CAN 오류 카운터 증가
- 카메라 source 2 중단

이 구간에는 28.842초부터 약 0.4초간 `steerTempUnavailable`이 있었고, 37.658초에는 가속 오버라이드 `0x2CB`가 한 번 차단됐다. 전자는 조향 제어의 일시적 사용 불가 이벤트로 종방향 ACC/CAN 붕괴와 별개이며, 후자는 CAN 붕괴 없이 지나갔다.

최신 실패 사례인 `L16`은 시작할 때부터 Panda 누적값에 `safetyTxBlocked=24`, bus 0 총 오류 55,529회, CAN core reset 141회가 기록돼 있었다. 이 값은 부팅 이후 누적값이므로 이전 구간에도 간헐적인 차단과 카메라 CAN 단절이 있었음을 의미한다. 해당 1분 동안에는 다시 100,725개의 오류와 255회의 core reset이 증가했다.

2026-08-07의 `L18`~`L20`은 이와 다르다. 사용자가 경고를 본 시점에도 Panda fault, 송신 차단, ACK 오류, CAN core reset 증가가 없었다. 따라서 이번 두 증상은 “물리 CAN이 먼저 끊겨 발생한 경고”가 아니라, CAN 전송은 살아 있는 상태에서 EBCM/ACC가 명령의 카운터 위상 또는 활성 순서를 거부한 사례다.

`L23`의 `steerTempUnavailable`은 약 34초에 알림만 발생했으며 종방향 `accFaulted`나 CAN invalid로 이어지지 않았다. 이 이벤트는 조향 토크/각도 제한, EPS 온도·허용 상태, 차종별 조향 설정을 별도로 확인할 항목이며 `fa2b434`에서는 변경하지 않았다.

## 14. 최종 판단

원래의 “규칙 없이 발생하는 크루즈 오류”는 실제로 규칙이 있었다. `0x2CB`의 특정 명령값/카운터 조합에서 체크섬 carry가 틀렸고, 차량은 약 52 ms 뒤 `accFaulted`를 냈다. 체크섬을 고친 뒤에는 순정 카운터와의 동기화 및 Trailblazer 고유 `0x370` 상태가 남은 차이로 확인돼 각각 수정했다.

그 후 로그에서 남은 직접적인 이상은 운전자 가속페달 전환 순간의 Panda 차단이었다. `8802d35`는 해당 주기부터 안전하게 허용되는 inactive 가스·리젠/제동 그룹을 보내도록 수정했다.

2026-08-07 로그에서는 두 가지 규칙이 더 확인됐다. 냉간 시동에는 실제 순정 `0x2CB`가 `0x2CD`보다 한 카운터 늦었고, 약한 제동으로 순정 ACC가 권한을 철회한 뒤에도 openpilot이 약 170 ms 동안 active 명령을 계속 보냈다. 두 경우 모두 경고 직전까지 Panda와 물리 CAN은 정상이어서 하드웨어보다 차량 ECU가 기대하는 메시지 순서 차이가 직접 원인이라는 결론이 강화됐다.

최종 커밋 `fa2b434`는 실제 순정 `0x2CB`의 도착 주기·카운터·활성 상태를 직접 따르고, `0x370`까지 순정 비활성 상태를 존중하며, 권한 해제 edge에서 즉시 명령 중립화와 디스인게이지를 수행한다. 집중 테스트 35개와 정적 검증을 통과했다.

따라서 현재 브랜치는 **로그로 확인된 모든 직접 원인에 대한 수정이 적용된 상태**다. 다만 `fa2b434`가 들어간 실차 rlog는 아직 없으므로 “완전 해결 확정”이 아니라 “코드상 해결, 냉간 시동 및 장거리 실차 검증 대기”로 관리한다.
